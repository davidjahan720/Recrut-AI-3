📐
Ce document décrit le socle minimal attendu.
Les blocs techniques, les phases et les fonctionnalités présentés ici constituent la brique fondamentale que chaque participant doit implémenter. C'est le minimum requis pour valider l'exercice.

Chaque participant est libre d'ajouter des fonctionnalités supplémentaires (filtres avancés, analytics, notifications en temps réel, dark mode, etc.) — à la condition expresse de respecter et livrer d'abord l'intégralité du socle minimal décrit ci-dessous. Les ajouts personnels ne doivent pas compromettre le fonctionnement de la brique de base.

Partie 1

Les blocs techniques de l'application

L'application se décompose en 6 blocs techniques clairement séparés. Chaque bloc a une responsabilité unique et communique avec les autres via des interfaces bien définies.

01 · Frontend
SPA React
Interface utilisée par l'équipe RecrutAI : login, dashboard, gestion des clients et des offres, consultation des candidatures.
React Vite Tailwind Shadcn/ui
02 · Base de données
Postgres Supabase
3 tables métier (clients, jobs, applications). Row Level Security activée pour que seuls les utilisateurs connectés puissent lire/écrire.
Supabase Postgres RLS
03 · Authentification
Supabase Auth
Email + mot de passe, clé en main. Session JWT gérée automatiquement. Comptes créés manuellement via le dashboard Supabase.
Supabase Auth JWT
04 · Edge Function
Scoring IA & notification
Reçoit le texte extrait du CV uploadé, appelle Claude pour le scoring, écrit le résultat en base, déclenche l'email si score ≥ 60. Le cœur logique de l'app.
Deno Supabase Functions
05 · APIs externes
Claude + Resend
Claude Sonnet 4.6 pour le scoring IA. Resend pour l'envoi transactionnel de l'email de qualification au client.
Anthropic API Resend API
06 · Déploiement
Vercel + Supabase CLI
Frontend déployé sur Vercel via connexion GitHub. Edge Function déployée via la CLI Supabase. Secrets gérés côté Supabase.
Vercel Supabase CLI GitHub
💡
Principe de séparation : le frontend ne parle jamais directement à Claude ou à Resend. Il parle seulement à Supabase (base + Storage + Edge Function). Les clés d'API externes ne quittent jamais l'Edge Function. C'est ce qui garantit la sécurité de l'application.

Partie 2

La stack retenue

Stack moderne, mature, et massivement documentée. Claude Code connaît parfaitement chacun de ces outils — le taux d'hallucination est quasi nul sur ce triplet React + Supabase + Vercel.

Frontend framework
React 18+

Bibliothèque UI la plus utilisée au monde. Écosystème massif, parfaitement intégré à Vercel et Supabase.

→ react.dev
Build tool & dev server

Démarrage instantané, hot-reload ultra-rapide. Le choix par défaut pour créer une SPA React moderne.

→ vitejs.dev
Styling

Framework CSS utility-first. Permet de styler rapidement sans quitter le JSX. Claude Code est excellent avec.

→ tailwindcss.com

Composants React pré-stylés (boutons, inputs, tables, dialogs…) copiés directement dans le projet. Zero dépendance, 100 % customisable.

→ ui.shadcn.com

Postgres managé + Auth + Edge Functions + Storage + Realtime. Une seule plateforme pour tout ce qui n'est pas frontend.

→ supabase.com/docs
IA générative

→ docs.anthropic.com
Email transactionnel

API d'envoi d'email la plus simple du marché. Plan gratuit : 3 000 emails/mois — largement suffisant pour le projet.

→ resend.com/docs
Hébergement & déploiement
Vercel

Déploiement du frontend connecté à GitHub. Chaque push déclenche une mise à jour automatique. URL publique en HTTPS incluse.

GitHub

Repo Git pour le code. Point de connexion entre Claude Code, Vercel, et l'équipe.

→ github.com
Assistant de développement

L'assistant IA qui génère le code, crée les fichiers, exécute les commandes. Le vrai moteur de la semaine de build.

Comptes à préparer avant le démarrage : un compte Supabase, un compte Vercel, un compte GitHub, une clé API Anthropic (crédit de 5 à 10 $ suffit), un compte Resend (plan gratuit).

Partie 3

Guide de développement semaine par jour

7 phases de build, ordonnées pour que chaque brique repose sur la précédente. Chaque phase est pensée comme une unité livrable : à la fin, quelque chose fonctionne et se voit.

Phase 0
Setup initial du projet
Créer l'environnement de travail · comptes, repo, projet Vite
Jour 1 matin · ~2 h
1
Initialiser le workspace

Créer le dossier de travail et y ouvrir Claude Code. Toutes les commandes suivantes seront lancées depuis ce dossier.

mkdir recrutai-workspace && cd recrutai-workspace
2
Créer le projet en TypeScript

À la création Vite, choisir le template react-ts. Shadcn/ui est conçu pour TypeScript (types des composants, meilleure complétion par Claude Code), et ça évite les erreurs silencieuses au runtime.

npm create vite@latest recrutai -- --template react-ts
3
Installer Tailwind + Shadcn/ui

Tailwind via la doc officielle Vite, puis Shadcn via son CLI. Shadcn installera automatiquement les dépendances nécessaires.

npx shadcn@latest init
# Choisir : TypeScript = oui, Style = default, Base color = slate

# Puis installer les composants qui seront utilisés
npx shadcn@latest add button input card table dialog form label textarea select badge
4
Créer le repo GitHub et le projet Supabase

Un repo GitHub pour le code, un projet Supabase pour la base. Les deux gratuits. Noter l'URL et la clé anonyme du projet Supabase (tableau de bord → Settings → API).

5
Installer le client Supabase

C'est la bibliothèque qui va permettre au frontend de parler à la base de données.

npm install @supabase/supabase-js
🤖
Avec Claude Code : demander "Setup le projet RecrutAI avec Vite + React + Tailwind + Shadcn/ui, et configure un client Supabase en lisant les variables d'environnement VITE_SUPABASE_URL et VITE_SUPABASE_ANON_KEY". Claude Code créera la structure de fichiers et le fichier lib/supabase.js.
Phase 1
Base de données & authentification
Créer les tables Supabase, activer Auth, router le login
Jour 1 après-midi · ~3 h
1
Créer les 3 tables métier dans Supabase

Via l'éditeur SQL du dashboard Supabase, exécuter le script de création des tables clients, jobs, applications selon le modèle défini dans le workflow fonctionnel.

2
Activer Row Level Security

Sur chaque table, activer RLS et créer une policy "authenticated users only" pour SELECT, INSERT, UPDATE. Sans ça, la base est accessible publiquement.

ALTER TABLE clients ENABLE ROW LEVEL SECURITY;
CREATE POLICY "authenticated_all" ON clients
  FOR ALL TO authenticated USING (true);
3
Créer un premier utilisateur dans Supabase Auth

Dashboard Supabase → Authentication → Users → Invite user. Entrer l'email de l'utilisateur et lui fixer un mot de passe.

4
Construire la page de login et la protection des routes

Une page /login avec les composants Shadcn, et un composant <ProtectedRoute> qui vérifie la session Supabase avant de rendre les pages de l'app.

🤖
Avec Claude Code : "Crée une page Login avec Shadcn (email + password), connecte-la à Supabase Auth, et ajoute un ProtectedRoute qui redirige vers /login si pas de session active. Utilise react-router-dom pour le routing."
Phase 2
Layout principal & navigation
Sidebar, header, structure des pages
Jour 2 matin · ~2 h
1
Créer le layout avec sidebar

Un layout persistant avec une sidebar à gauche (Dashboard, Clients, Offres, Candidatures) et le contenu principal à droite. Le bouton de déconnexion est dans le coin de la sidebar.

2
Créer les routes vides

Créer les 4 routes : /dashboard, /clients, /jobs, /applications. Pour l'instant, des pages vides qui affichent juste leur titre.

3
Afficher le nom de l'utilisateur connecté

Dans le header ou la sidebar : récupérer l'email de la session Supabase et l'afficher en haut de la sidebar.

Phase 3
CRUD Clients
Liste, création, modification des clients
Jour 2 après-midi · ~3 h
1
Liste des clients

Table Shadcn avec les colonnes : nom, contact, email notification, secteur, nombre d'offres actives. Récupérer les données via supabase.from('clients').select().

2
Création d'un client

Bouton "Nouveau client" qui ouvre un Dialog Shadcn avec un formulaire. À la soumission : supabase.from('clients').insert(), puis rafraîchissement de la liste.

3
Modification et suppression

Un bouton par ligne pour éditer (rouvre le Dialog pré-rempli), un bouton pour supprimer (avec confirmation). update() et delete() côté Supabase.

4
Fiche client (page détail)

Route /clients/:id qui affiche les infos du client et la liste de ses offres.

Phase 4
CRUD Offres + upload de CV
Liste, création d'offre, zone de dépôt de CV (PDF)
Jour 3 matin · ~3 h
1
Liste des offres

Table avec les colonnes : titre, client, localisation, type de contrat, statut, nombre de candidatures. Filtre par statut (active / clôturée).

2
Création d'une offre

Formulaire avec : titre, client (select parmi les clients existants), localisation, type de contrat, description (textarea grande taille), et seuil de qualification (champ numérique 0–100, défaut 60). À la soumission, insertion en base.

3
Fiche offre avec zone d'upload de CV

Sur la page détail d'une offre, intégrer une zone de dépôt (drag & drop ou sélection) pour uploader un ou plusieurs CV au format PDF. Aucun champ de métadonnée à saisir : le nom et l'email du candidat seront extraits automatiquement par Claude à partir du texte du CV.

4
Créer le bucket Supabase Storage

Créer un bucket cvs dans Supabase Storage (dashboard → Storage → New bucket). Le laisser privé (ne pas cocher "Public bucket"). Configurer les policies pour que seuls les utilisateurs authentifiés puissent uploader et lire les fichiers.

-- Policies SQL pour le bucket cvs
CREATE POLICY "authenticated_upload" ON storage.objects
  FOR INSERT TO authenticated
  WITH CHECK (bucket_id = 'cvs');

CREATE POLICY "authenticated_read" ON storage.objects
  FOR SELECT TO authenticated
  USING (bucket_id = 'cvs');
5
Flux d'upload côté frontend

Après chaque dépôt de fichier : (1) uploader le PDF dans Storage, (2) récupérer le file_path, (3) appeler l'Edge Function score-cv avec { job_id, cv_file_path }. Afficher un statut pending dans l'UI, puis rafraîchir quand la réponse arrive.

📎
Un kit de test sera fourni : 3 offres prêtes à l'emploi (descriptions complètes) + 5 CV PDF par offre, avec des scores attendus indicatifs pour valider le bon fonctionnement du scoring de bout en bout.
Phase 5
Edge Function — scoring IA & notification email
La partie la plus délicate : appel Claude, scoring, envoi Resend
Jour 3 après-midi + Jour 4 · ~6 h
1
Installer la CLI Supabase et initialiser les functions 
npm install -g supabase
supabase login
supabase init
supabase functions new score-cv
2
Configurer les secrets de l'Edge Function

Les 3 secrets nécessaires, à définir dans le dashboard Supabase (Edge Functions → Secrets) ou via la CLI.

supabase secrets set ANTHROPIC_API_KEY="sk-ant-..."
supabase secrets set RESEND_API_KEY="re_..."
supabase secrets set SYSTEM_PROMPT="Tu es un expert en recrutement..."
3
Extraire le texte du PDF avec unpdf (Deno)

La librairie unpdf fonctionne nativement en Deno (zero-dep, pas de binaire natif). Elle lit un ArrayBuffer et renvoie le texte page par page.

// dans l'Edge Function
import { extractText } from "https://esm.sh/unpdf";

// 1. Télécharger le PDF depuis Storage
const { data: file } = await supabase.storage
  .from('cvs').download(cv_file_path);
const buffer = await file.arrayBuffer();

// 2. Extraire le texte
const { text } = await extractText(new Uint8Array(buffer), { mergePages: true });
4
Écrire la logique complète de la fonction

Séquence complète exécutée par l'Edge Function à chaque appel depuis le frontend :

// 1. Lire le body : { job_id, cv_file_path }
// 2. Vérifier que l'offre existe + est active + récupérer score_threshold
// 3. Créer la candidature (status = 'pending', cv_file_path)
// 4. Télécharger le PDF depuis Storage → extraire texte (unpdf)
// 5. Appeler Claude : SYSTEM_PROMPT + cv_text + job.description
//    → attendu : { score, justification, candidate_name, candidate_email }
// 6. Comparer score au score_threshold de l'offre
// 7. UPDATE applications (score, justification, candidate_name,
//    candidate_email, cv_text, status = qualified | rejected)
// 8. Si qualified : appeler Resend → UPDATE email_sent_at
// 9. Tout le corps dans un try/catch :
//    toute exception → status = 'error', justification = err.message
// 10. Retourner 200 + résultat (ne jamais renvoyer 500 au frontend)
5
Configurer Resend avec un domaine de test

Resend refuse l'envoi tant que le domaine from n'est pas vérifié. Pour le dev / la démo, utiliser l'adresse onboarding@resend.dev fournie par Resend (fonctionne sans vérification DNS). En production réelle, il faudra vérifier un vrai domaine.

await resend.emails.send({
  from: "RecrutAI <onboarding@resend.dev>", // dev uniquement
  to: client.notification_email,
  subject: `Nouveau CV qualifié — ${candidate_name}`,
  html: `...`,
});
6
Tester en local puis déployer 
# Test local avec hot-reload
supabase functions serve score-cv --env-file .env.local

# Déploiement quand tout passe
supabase functions deploy score-cv

Pas besoin du flag --no-verify-jwt : la fonction est appelée depuis le frontend authentifié, le token JWT est transmis automatiquement par le client Supabase. Si un appel externe (curl, Postman) est nécessaire pour debug, ajouter le flag --no-verify-jwt ponctuellement.

7
Tester de bout en bout avec le kit de CV fournis

Sur une offre créée, déposer les PDF du kit de test. Vérifier : scoring déclenché, score + justification + nom + email affichés dans le dashboard, email bien reçu pour les CV qualifiés (> seuil de l'offre), statut error absent.

🤖
Avec Claude Code : lui donner l'objectif complet en une seule prompt, en lui précisant les noms des secrets, la structure de la base (avec score_threshold et cv_file_path), le format JSON attendu de Claude. Claude Code écrira l'Edge Function entière (Deno/TypeScript) et la déploiera.
⚠️
Ne jamais renvoyer 500 au frontend. Toutes les erreurs (PDF illisible, JSON Claude malformé, Resend KO) doivent être capturées et traduites en status = 'error' dans la base. L'utilisateur doit voir la candidature passer en état "erreur" dans la liste, pas une notification d'échec brute.
Phase 6
Dashboard & consultation des candidatures
Lecture des scores, stats, justifications
Jour 5 matin · ~3 h
1
Page candidatures par offre

Sur la fiche offre, afficher la liste des candidatures triée par score décroissant : nom, email, score (badge coloré selon ≥ seuil de l'offre ou < seuil), statut (qualifié / rejeté / erreur), justification IA, date, lien de téléchargement du PDF original.

2
Dashboard global

Page /dashboard avec 4 cartes de KPI : offres actives, CV reçus aujourd'hui, CV qualifiés cette semaine, taux de qualification global. Calculer ces stats via des requêtes SQL Supabase.

3
Filtres et tris

Ajouter la possibilité de filtrer les candidatures par statut (qualifié / rejeté / en erreur), et de trier par score ou date.

Phase 7
Déploiement final sur Vercel
Mise en production, variables d'environnement, test end-to-end
Jour 5 après-midi · ~2 h
1
Push final sur GitHub

S'assurer que tout le code est committé et poussé sur la branche principale.

2
Connecter Vercel à GitHub

Depuis le dashboard Vercel : Import Project → sélectionner le repo GitHub → Vercel détecte automatiquement que c'est un projet Vite.

3
Configurer les variables d'environnement Vercel

Dans les settings du projet Vercel, ajouter VITE_SUPABASE_URL et VITE_SUPABASE_ANON_KEY. Redéployer.

Test end-to-end en production

Créer un client, créer une offre, uploader les faux CV fournis sur la fiche de l'offre, vérifier que les scores apparaissent, qu'un email est bien reçu pour les CV qualifiés, et que tout s'affiche correctement dans le dashboard.

✓
À la fin de cette phase, l'application est en production : URL publique HTTPS, base de données fonctionnelle, endpoint API prêt à recevoir des CV, scoring IA opérationnel, emails clients automatiques. C'est livré.

Points d'attention critiques pour la semaine

⚠️
Ne jamais mettre de clé API dans le frontend. ANTHROPIC_API_KEY et RESEND_API_KEY ne doivent exister QUE dans les secrets Supabase (Edge Function). Si elles apparaissent dans le code React, elles seront visibles publiquement.
⚠️
Activer Row Level Security dès le début. Sans RLS, n'importe qui avec l'URL Supabase peut lire/modifier la base. C'est l'erreur la plus fréquente sur Supabase.
⚠️
Contraindre Claude à répondre en JSON strict. Dans le system prompt, imposer explicitement le format {"score": int, "justification": string, "candidate_name": string|null, "candidate_email": string|null} et rien d'autre (pas de markdown, pas de texte avant/après). Sinon, le parsing de la réponse échoue aléatoirement.
⚠️
Le bucket Storage cvs doit rester privé. Un CV contient des données personnelles. Jamais de bucket public. Les liens de téléchargement doivent passer par createSignedUrl() avec une expiration courte (1h max).
💡
Tester d'abord l'upload + scoring avec les CV du kit fourni. Uploader un seul CV de test sur une offre et vérifier que le score apparaît bien dans le dashboard. Quand le flux fonctionne pour un CV, passer au multi-upload.
